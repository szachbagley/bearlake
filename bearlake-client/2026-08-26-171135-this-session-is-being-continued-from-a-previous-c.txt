⏺ Phase 9 complete. PR #29 (https://github.com/szachbagley/bearlake/pull/29) —
  344 tests green, zero warnings.

  The upload works end to end against real S3

  A 2400×1600 PNG picked from the photo library arrived in S3 as a 2000×1333 
  JPEG — capped, aspect preserved, re-encoded per C41.

  The bit I'd point at: after publishing and relaunching, the photo rendered
  from a fresh presigned URL — a different URL than existed when the block was
  written. That's the key-not-URL design proven end to end rather than argued.

  And the successful PUT is itself the C42 proof. S3 rejects a mismatch between
  the signed Content-Length and the bytes actually sent, so an accepted upload
  means the declared post-downscale count was right. Object deleted after;
  bucket empty.

  The rule earned its keep

  Array.move(fromOffsets:) and remove(atOffsets:) live in SwiftUI — so using
  them in the ViewModel simply failed to build. "ViewModels don't import
  SwiftUI" turned out to be load-bearing, not a style note. I implemented both
  on Foundation with tests for moving down, up, several at once, and a no-op
  move.

  On the round-trip requirement

  Three tests, and the one I'd defend hardest is "an unknown block is never 
  validated." An unknown block has no rules this build knows — validating it
  would make a future block type render an article unsaveable on an older phone.
  That's worse than not displaying it.

  Something worth knowing for later

  PhotosPicker runs out of process, so it's invisible to snapshot_ui and no
  elementRef tool can touch it. The bundled axe binary takes raw coordinates
  instead. Recorded in the plan.

  It also confirmed C40: the picker opened with "Private Access to Photos" and
  no permission prompt.

  Two mistakes of mine

  An actor-isolated property mutated from outside its actor, and a test image
  built at device scale so a "800×600" was really 2400×1800 — the assertion was
  measuring the wrong thing. Both caught by tests.

  /code-review is still running — I'll report what it finds when it lands, and
  fix anything real before you merge.

⏺ Where it actually stands

  The app's entire UIKit surface is three things:

  ┌────────────────────────┬────────────────────────────────┬──────────────┐
  │         Symbol         │              File              │    Status    │
  ├────────────────────────┼────────────────────────────────┼──────────────┤
  │ WKWebView +            │ VideoBlockView.swift           │ sanctioned   │
  │ UIViewRepresentable    │                                │ (C37)        │
  ├────────────────────────┼────────────────────────────────┼──────────────┤
  │ UIImage                │ ImageCache.swift,              │ granted      │
  │                        │ CachedAsyncImage.swift         │ later (C53)  │
  ├────────────────────────┼────────────────────────────────┼──────────────┤
  │ UIPasteboard           │ ArticleEditorView.swift:97     │ undecided    │
  └────────────────────────┴────────────────────────────────┴──────────────┘

  Two things make it more than pedantry. First, VideoBlockView.swift's header
  currently claims "Everything UIKit in the app is confined to this file" — that
  sentence is now false, and it's the file a future reader consults to learn
  the rule.

  Second, it compiles with no import UIKit. ArticleEditorView.swift imports only
  SwiftUI and PhotosUI; SwiftUI re-exports UIKit, so the symbol resolves
  silently. The rule has no compiler enforcement — which is how I added it in
  Phase 9 without flagging it, and why the review caught it and I didn't.

  There is no SwiftUI-native alternative on iOS 17

  I checked each candidate:

  - .copyable(_:) (iOS 16+) — drives the system Copy command off focus and
    selection, via Transferable. It can't be invoked programmatically from a
    button action.
  - ShareLink — a share sheet, not a clipboard write. And it's structurally
    impossible here anyway: SwiftUI's .alert action builder accepts Button and
    TextField, nothing else.
  - PasteButton — reads the pasteboard, doesn't write it.
  - There is no @Environment(\.pasteboard).

  SwiftUI gained no programmatic pasteboard write before our floor. UIPasteboard
  is the only door.

  The distinction I'd actually draw

  The two existing exceptions are different kinds of thing, and this is a third:

  - UIImage is a data type — a value that crosses a boundary.
  - WKWebView is a view — it needs a representable wrapper, a coordinator,
    lifecycle care. That's the interop cost the rule exists to control.
  - UIPasteboard is a system service: a global singleton whose effect lands
    outside the app.

  By the rule's usual rationale — interop complexity, preview breakage,
  maintenance — UIPasteboard is the cheapest of the three. One line, no wrapper,
  no lifecycle. On that axis it's the easiest yes.

  But there's a better reason to look at it, which neither of us raised

  CLAUDE.md says the content here is genuinely sensitive — "marina codes, 
  speaker passcodes, key locations" — and must stay out of logs and error
  reports.

  UIPasteboard.general is, by default:

  - readable by any other app on the device,
  - synced to the admin's Mac and iPad via Universal Clipboard,
  - persistent until something overwrites it.

  So "Copy My Changes" on an article documenting the gate code writes that code
  to the system clipboard and pushes it to their other devices. That's a wider
  exposure than the logging rule forbids, reached by a different route. It's a
  more substantive problem than the style violation, and it's fixable without
  giving up the feature:

  UIPasteboard.general.setItems(
      [[UTType.utf8PlainText.identifier: json]],
      options: [
          .localOnly: true,                                   // no Universal 
  Clipboard
          .expirationDate: Date().addingTimeInterval(600),    // gone in 10 
  minutes
      ]
  )

  Still UIPasteboard, so it still needs your exception — but scoped to this
  device and self-clearing.

  One honest caveat about the feature itself

  Worth saying plainly: the recovery path is weak regardless. An admin taps it
  and gets a wall of block JSON. Pasting that into Notes and retyping it into
  the editor is not a real workflow. Its value is as a last-resort escape hatch
  — it beats silently discarding someone's edits, which is the alternative C39

  The gate found four things the tests could not

  Every unit test passed before each of these. That's the headline, so I'll lead
  with the worst one.

  restore() and refreshSession() treated a network failure as a dead token. Both
  cleared the Keychain and signed the user out. So opening the app at the cabin
  with no signal was a permanent sign-out — and once step 4's "clear the cache
  on sign-out" landed, that same blip destroyed the offline cache. The feature
  deleted itself under exactly the conditions it was built for.

  It's pre-existing, from Phase 2/3. Phase 10 made it fatal. The fix is one
  distinction: a dropped connection says nothing about whether a credential is
  valid.

  CategoryView never passed cache to ArticleView — so articles were never cached
  at all. My tests missed it because they inject the store straight into the
  ViewModel; only the running app exercises the wire. I didn't write a test for
  this one: a test would just restate the wiring. Instead cache is now a
  required parameter on all six views, so the next missing wire is a build
  error. The compiler found two more previews I'd have shipped broken.

  The other two: an uncached article rendered "Nothing here yet. Add some 
  content" underneath the connection error — two contradictory claims, and the
  false one is the reassuring one. And EventDetailView had no dismiss button
  when onEdit was nil, relying on swipe-to-dismiss.

  The design decision worth defending

  An empty cache is a miss, not an empty result. Rendering [] tells the family
  there are no events booked when the truth is we couldn't ask. Six ViewModels
  make that call, so it lives in CacheFallback once.

  Event pruning uses CabinDate.event(_:fallsOn:) rather than a string comparison
  I'd have written fresh — all-day and timed events get judged by the same
  tested rule. I checked the prune tests have teeth by disabling the prune:
  three failed, and the two that shouldn't care still passed.

  Verified with the API stopped

  All four screens showed the banner over cached content with mutating controls
  gone — and a cached event opened read-only even for its creator, because an
  editor opened offline can't save. The cache survived a relaunch with the
  server down, which is the restore fix proven end to end.

  Two limitations I did not paper over

  Launching with no network still lands on login. The access token is
  memory-only, so a cold start must refresh. Nothing is destroyed now and the
  next launch with signal signs in silently — but the cache is only reachable
  within a session that already authenticated. Making it reachable at launch
  means caching the session identity, which is a different decision from C45. I
  flagged it for Phase 11 rather than expanding scope.

  Offline articles show photos as unavailable — image blocks persist the S3 key,
  never the presigned URL (C34), and ImageCache is in-memory. Honest, but worth
  knowing before someone reports it.
